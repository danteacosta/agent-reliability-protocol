# ARP 3.0 Design

## Decision

ARP 3.0 is the canonical wire contract for new producers. ARP 0.1 and 2.x
remain readable through explicit adapters, but their domain-shaped fields are
not serialized by v3 producers.

The protocol stays dependency-free and domain-neutral. Delivery, retrieval,
and requirement-quality systems use namespaced profiles and referenced
artifacts for their domain facts.

## Canonical records

### Run manifest

`RunManifest` records only generic reproducibility facts:

- `schema_version`;
- `run_id` and `created_at`;
- `source.revision`, `source.input_ref`, and `source.input_hash`;
- `executor.name` and `executor.version`;
- `configuration_hash`;
- `environment`;
- optional `profile`;
- explicit `capture_policy`;
- opaque, namespaced `extensions`.

The core does not define fields named after trackers, repositories, models,
providers, harnesses, datasets, waves, or domain metrics. A delivery adapter
maps its base revision and graph snapshot into `source` and puts PR, CI,
review, merge, and work-item facts in `software-delivery/v1` extensions or
artifacts.

### Episode identity and lifecycle event

An episode is identified by `run_id` and `episode_id`. Optional ordinal and
variant references remain generic. Lifecycle events use the same identity,
strict sequence numbers, stable timestamps, and opaque extension payloads.
No v3 event requires `experiment_id` or `replication_id`.

### Evidence

`EvidenceRecord` is a standalone record. It contains a generic claim, scalar
observation/expectation, optional comparator, source event, artifact URI/hash,
stage, capture policy, and extensions. Complex or sensitive material belongs
in an artifact governed by the capture policy; it is never smuggled into a
numeric metric field.

### Gates

`GateRequest` means that a decision is pending and lists the evidence IDs
required by a policy. `GateDecision` is emitted only after a decision is
resolved. A pending human merge is therefore not a `block`; missing or
contradictory evidence can produce `request_clarification` or `block` only
when the policy actually decides that outcome.

## Compatibility

Adapters map v0.1/2.x manifests, events, evidence, and decisions into v3.
Legacy identity fields are preserved only under `arp-compat/v2` extensions.
The adapter is lossy where the old contract had no generic equivalent, and it
must never pretend that an absent field was independently observed.

## Control-plane integration

The control-plane core owns `WorkAttempt`, `DeliveryVerification`, and
`HumanGate`. It exposes a `ReliabilityRecorder` port and does not import ARP.
The ARP adapter emits:

```text
WorkAttempt          -> RunManifest + EpisodeIdentity
delivery observation -> EvidenceRecord + delivery artifact
pending gate         -> GateRequest
resolved gate        -> GateDecision
```

The `software-delivery/v1` profile carries work-item, attempt, base/head SHA,
PR, CI, review, merge, graph, and wave references. A merge is profile evidence,
not a new ARP lifecycle checkpoint. Downstream scheduling still requires an
independently verified approval and a newly observed base revision.

## Acceptance scenarios

1. A delivery attempt can emit a v3 manifest without dataset, model, provider,
   harness, or tracker fields.
2. A v2 manifest can be adapted to a valid v3 manifest while retaining its
   original identity in a compatibility extension.
3. Evidence records reject arrays and objects in scalar observation fields.
4. A gate request validates as pending; no gate decision is emitted until the
   gate has an outcome.
5. A v3 lifecycle sequence rejects duplicate identities and non-contiguous
   sequence numbers.
6. Three independent delivery attempts can record verified merge evidence,
   after which a fourth attempt receives a new source revision.
